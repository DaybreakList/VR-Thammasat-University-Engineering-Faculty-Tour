กรอบสีเขียวคือส่วนของภาพ 360° ที่ผู้ชม (หรือ API) กำลังร้องขออยู่ ณ ขณะนี้ — นี่คือหลักการเดียวกับ viewport-adaptive streaming ที่ใช้ลดแบนด์วิดท์ในสตรีม 360° จริง โดยส่งเฉพาะส่วนที่ผู้ชมกำลังมองเป็นคุณภาพสูง

สิ่งที่ดีโมนี้จำลองไว้แล้ว

  • เซิร์ฟเวอร์ 360° จำลอง — สร้างภาพ equirectangular ขึ้นในเบราว์เซอร์แทนกล้องจริง
  • API เสมือนสำหรับขอเฟรมภาพ พร้อม yaw / pitch / fov / mode
  • โหมด 360° เต็มทรงกลม และ 180° ครึ่งซีก (จำกัดช่วง yaw)
  • ตัวเชื่อมต่อแว่น VR ผ่าน WebXR (ถ้าอุปกรณ์รองรับ)
  • ภาพ viewport ที่ทับซ้อนบนภาพ equirect ต้นฉบับแบบเรียลไทม์

ตัวอย่าง REST API ที่ควรออกแบบจริง

GET /api/v1/stream/frame ?yaw=0&pitch=0&fov=90&mode=360 GET /api/v1/stream/hls/playlist.m3u8 ?mode=180 WS /api/v1/stream/live → client ส่ง viewport ปัจจุบันทุก ~200ms ← server ส่งเฉพาะ tile คุณภาพสูงในมุมนั้น

ขั้นถัดไปสำหรับกล้องและแว่นจริง

  • เชื่อมกล้องจริง: กล้อง 360° ส่วนใหญ่ (Insta360, Ricoh Theta, Kandao) ส่งสตรีมออกเป็น RTMP/RTSP หรือ USB UVC — ใช้ FFmpeg/GStreamer รับภาพเข้าเซิร์ฟเวอร์แทนภาพจำลอง
  • ลด latency: สำหรับ interactive viewport ใช้ WebRTC แทน HLS (latency ต่ำกว่า 1 วิ เทียบกับ 3–10 วิ)
  • ประหยัดแบนด์วิดท์: ทำ tiled streaming — แบ่ง equirect เป็นกริดย่อย ส่งเฉพาะ tile ที่อยู่ใน viewport เป็นความละเอียดสูง ส่วนที่เหลือส่งความละเอียดต่ำ
  • เชื่อมแว่น VR จริง: ใช้ WebXR (เบราว์เซอร์ในแว่น เช่น Quest Browser) หรือแอป native ผ่าน OpenXR — โครงสร้าง sphere + texture เดียวกับดีโมนี้ใช้ได้ทันที
  • การยืนยันตัวตน/สิทธิ์: เพิ่ม token ต่อ session สำหรับ API และ WebSocket ก่อนใช้งานจริง
